# Publishing evalkit

Everything the repository needs to exist on GitHub, written down before the
repository is created so that creating it is a transcription rather than a
series of small decisions taken at the API.

Written at tick 217, seven days after the date `D15` gave this project, because
the release could not have happened on that date: there was no
`.github/workflows/pages.yml` in the tree, so turning Pages on would have
published nothing, and no file said what the About box should contain. Both are
here now. `agentscope`'s publication an hour earlier is where the shape of this
document comes from.

## The About box

**Description**, 350 characters or fewer, and it has to carry the number:

> A published comparison of two models moved its headline metric by 5.3 rows
> out of 10,578. The smallest difference that sample can detect is 178, so three
> of its four metrics cannot be called at all. Drag the bar and watch the
> verdict turn over, then watch it turn back at the difference that was actually
> published.

**Homepage**: `https://broikos-nikos.github.io/evalkit/`

**Topics**, ten, the maximum GitHub shows without a fold:

```
evaluation  statistics  machine-learning  benchmarking  statistical-power
mcnemar-test  reproducible-research  typescript  data-visualization  nlp
```

`statistical-power` and `mcnemar-test` are the two that matter. Somebody who
has just been handed two accuracy numbers and a decision to make is searching
one or the other, and the thing nobody else has published is the instrument:
the refusal is computed on the page, from the sample size, in front of the
reader, rather than asserted in a paragraph.

`evaluation` and `benchmarking` are there for the people who arrive with the
opposite instinct, looking for a leaderboard, because they are the readers this
page is actually for.

The topics name the category and not the tool, which is `D22`.

## Settings

- **Public**, no wiki, no projects, no discussions. Issues on: a repository
  whose whole argument is an arithmetic result should be reachable by somebody
  who thinks the arithmetic is wrong.
- **Pages**: source GitHub Actions, not a branch. The workflow builds, gates and
  deploys, and a branch source would publish whatever was committed regardless
  of whether the gates passed. For this project that is not a formality: the
  page's claim is a power calculation, and a branch source would let a broken
  one reach a reader.
- **No default community files.** The MIT LICENSE is committed already, and
  `check:licence` fails if the README claims a licence the tree does not carry.

## The order, and why this order

1. **Create the repository** with the description, homepage and topics above, so
   the About box is never empty. `watch-it-think` shipped with an empty one and
   a recruiter audit filed it as a high finding: the ten second screen had no
   sentence on it.
2. **Push `main` with the whole history**, every commit authored
   `Nikos Broikos <broikos.nikolaos@gmail.com>`, none co-authored. Two commits
   here were authored `Broikos-Nikos` until tick 217, when the branch was
   rewritten before any of it was public; the tree hash was identical
   afterwards and the diff against the pre-rewrite branch was empty.
3. **Turn Pages on** and let the workflow run. Nothing is deployed by hand.
4. **Wait for the deploy, then open the live URL in a browser and look at it.**
   The deploy going green is not the same as the page working, and on
   `watch-it-think` the difference was two and a half seconds of `n/a` on the
   only element a non technical reader could use.
5. **Put the live link in the first screen of the README**, above the picture.

## What this does not claim

The numbers it judges are `watch-it-think`'s, measured by that project's own
quantiser and recorded in its `meta.json`. This repository recomputes the
verdict from them; it does not re-measure the models. That is why the input
table is generated by `npm run build:input` and held by `check:input` rather
than typed.
